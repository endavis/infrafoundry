# Dependabot Auto-merge

The workflow at `.github/workflows/dependabot-automerge.yml` evaluates each
dependabot PR and enables GitHub's native auto-merge for PRs that meet the
project's safety criteria. Qualifying PRs are merged automatically once the
required CI checks pass.

The label-driven opt-out path lives in a sibling workflow,
`.github/workflows/dependabot-blocked-label.yml`, which fires only on
`pull_request_target: labeled` events. Splitting label handling out of the
main workflow keeps the `Dependabot Auto-merge` check clean (it runs once per
PR open/sync, not once per auto-applied label) and lets the main workflow use
`concurrency: cancel-in-progress: true` safely.

## What gets auto-merged

A dependabot PR qualifies when **all** of the following are true:

- The update type is `version-update:semver-patch` or `version-update:semver-minor`.
- None of the updated dependency names match a glob in the
  `sensitive_dependencies` list.
- The PR has no label listed in `blocking_labels`.

Qualifying PRs receive:

- The `ready-to-merge` label applied automatically (satisfying the Merge Gate).
  This happens first and is **unconditional** for qualifying PRs.
- GitHub's native auto-merge attempted with the **squash** strategy. This step
  can fail for reasons outside the workflow (e.g. the repository does not have
  [`allow_auto_merge`](github-repository-settings.md#repository-settings) enabled),
  in which case the run is marked as a failure but the label above is already
  applied.
- A sticky status comment describing the outcome. If auto-merge was enabled, it
  confirms that; if the auto-merge step failed, it notes that the label was
  applied anyway and points at the workflow logs so a maintainer can investigate
  and/or merge manually.

## What gets skipped

A PR is skipped (no auto-merge, sticky comment posted for human review) when:

- The update is a **major version bump** (`version-update:semver-major`).
- A **sensitive dependency** is touched (e.g. anything matching `*ssl*`,
  `*security*`, `auth*`, `crypt*`, `*jwt*`, `*oauth*`).
- A **blocking label** (`do-not-merge` or `automerge-blocked`) is present.

Skipped PRs require a human reviewer to merge them using the normal workflow.

## The `automerge-blocked` opt-out

To stop auto-merge on a PR that already qualified, add the label
`automerge-blocked` (or `do-not-merge`). The `dependabot-blocked-label.yml`
workflow reacts to the `labeled` event:

- Disables GitHub's auto-merge on the PR.
- Removes the `ready-to-merge` label.
- Posts a sticky comment recording the block.

Both workflows share the same `<!-- dependabot-automerge:status -->` sticky
comment marker, so toggling the block updates the existing comment instead of
producing a thread of status messages.

## Required GitHub App configuration

The auto-merge workflow applies the `ready-to-merge` label using a **GitHub
App token** rather than the default `GITHUB_TOKEN`. This is not optional for
full end-to-end automation — it is required for the Merge Gate to re-run on
the `labeled` event so the `require-label` status check can flip from
`FAILURE` to `SUCCESS`.

### Why the App is needed

Events generated by the workflow's default `GITHUB_TOKEN` are deliberately
prevented from triggering further workflow runs. This is a GitHub-wide
loop-prevention rule documented in
[Triggering a workflow from a workflow](https://docs.github.com/en/actions/using-workflows/triggering-a-workflow#triggering-a-workflow-from-a-workflow).
If the workflow applies the `ready-to-merge` label with `GITHUB_TOKEN`, the
`labeled` event fires — but the Merge Gate workflow does **not** re-run on
it. The PR then sits indefinitely with a stale `require-label: FAILURE`
check even though the label is present.

Labels applied via a GitHub App **do** trigger downstream workflows, so the
Merge Gate re-runs and `require-label` turns green on its own.

### How the label step resolves the token

The `Add ready-to-merge label` step reads:

```yaml
env:
  GH_TOKEN: ${{ steps.app-token.outputs.token || secrets.GITHUB_TOKEN }}
```

- **App configured** (`vars.RELEASE_APP_ID` set): the App-token step runs,
  the label is applied with the App's identity, and the Merge Gate re-runs
  automatically.
- **App not configured** (`vars.RELEASE_APP_ID` empty): the App-token step
  is skipped by its `if:` guard, `steps.app-token.outputs.token` is empty,
  and the expression falls through to `secrets.GITHUB_TOKEN`. The label is
  still applied so the Merge Gate criterion is technically satisfied, but
  the check won't re-run until something else nudges it.

### Configuring the App

Follow the full setup in
[GitHub Repository Settings → Release Permissions](../../.github/CONTRIBUTING.md#recommended-github-app).
The auto-merge workflow reuses the same App as the release workflow. When
creating or updating the App, ensure the repository permissions include:

- **Contents:** Read and write
- **Metadata:** Read-only
- **Pull requests:** Write (required for `gh pr edit --add-label`)

Store the credentials as:

- **Variable:** `RELEASE_APP_ID` (the numeric App ID)
- **Secret:** `RELEASE_APP_PRIVATE_KEY` (contents of the `.pem` file)

### The three sticky-comment states

The sticky comment step posts different copy depending on the combination
of `AUTOMERGE_OUTCOME` and `APP_TOKEN_CONFIGURED`:

| State | Trigger | Message |
| :--- | :--- | :--- |
| **Success** | Auto-merge call succeeded | Auto-merge enabled; PR will merge when CI passes. |
| **Merge failed, App configured** | App token generated, but `gh pr merge --auto` failed | Label applied; maintainer should investigate the merge failure and merge manually. |
| **Merge failed, App not configured** | Both App token missing and merge call failed (or skipped) | Label applied via `GITHUB_TOKEN`; Merge Gate will **not** re-run on its own. User must remove and re-add the `ready-to-merge` label manually, or configure the App. |

### Manual workaround when the App is not configured

If the sticky comment indicates the App is not configured, you can unstick
the PR by toggling the label as your own user:

1. Click **Labels** on the PR sidebar.
2. Remove `ready-to-merge`.
3. Re-add `ready-to-merge`.

Your user account (not `GITHUB_TOKEN`) is a real actor, so the `labeled`
event fires normally and the Merge Gate re-runs. The long-term fix is to
[configure the App](#configuring-the-app) so this step is not needed again.

## Configuration

Lists live in `.github/automerge-config.json`:

```json
{
  "sensitive_dependencies": ["crypt*", "*ssl*", "*security*", "auth*", "*jwt*", "*oauth*"],
  "allowed_update_types": ["version-update:semver-patch", "version-update:semver-minor"],
  "blocking_labels": ["do-not-merge", "automerge-blocked"]
}
```

Globs use `*` as a wildcard and are matched case-insensitively against the full
dependency name. Edit the file via a normal PR to change policy.

## Version-update cooldown

To defend against supply-chain attacks that publish malicious versions and
are detected and yanked within hours-to-days, the `uv` ecosystem entry in
`.github/dependabot.yml` sets a 7-day
[`cooldown`](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference#cooldown--):

```yaml
cooldown:
  default-days: 7
  include:
    - "*"
```

Dependabot waits 7 days from a new version's release date before opening a
PR for it, so a malicious release that is yanked within a few days never
produces a PR to auto-merge.

**Security-update PRs bypass cooldown.** Per the dependabot docs: *"the
`cooldown` option is only available for version updates, not security
updates."* Advisory-driven PRs continue to land at full speed, so CVE
patching latency is unchanged.

**The `github-actions` ecosystem is not covered.** Dependabot's `cooldown`
only supports SemVer ecosystems and explicitly excludes `github-actions`.
Action bumps continue to flow through auto-merge under the existing
`automerge-config.json` rules; tighter handling for actions is tracked
separately.

## Grouped updates

Some dependencies are separate packages to dependabot but a single unit at
runtime. Bumping them independently produces PRs that each fail, and — because
each holds only half the change — none of them can be merged to unblock the
others. `.github/dependabot.yml` uses
[`groups`](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference#groups--)
to keep such a set in one PR.

The `github-actions` ecosystem groups the CodeQL action:

```yaml
groups:
  codeql-action:
    patterns:
      - "github/codeql-action*"
```

`github/codeql-action/init` writes a config file stamped with its own version,
and `github/codeql-action/analyze` refuses to load a config written by a
different one:

```
Loaded a configuration file for version '4.37.8', but running version '4.37.9'
```

Ungrouped, the 4.37.9 bump arrived as PRs #794 and #795 — one bumping `init`,
one bumping `analyze` — and both failed the required `CodeQL` check
(issue #799). Grouping is the fix; the bump itself then had to be applied by
hand because neither split PR could pass on its own.

Two tests guard this. `tests/test_dependabot_config.py` asserts the group
still matches both sub-actions — and that no group matches one without the
other, which would recreate the split. `tests/test_codeql_workflow.py` asserts
the two are in fact pinned to the same SHA today.

Grouping does not change auto-merge eligibility: `github/codeql-action` is not
in `sensitive_dependencies`, and the group's `update-type` is the highest of
its members, so a grouped patch bump still qualifies.

### Minor and patch catch-all

Each ecosystem also has a last group, `minor-and-patch`, matching `*` with
`update-types: ["minor", "patch"]`, so a weekly batch arrives as one PR rather
than one per dependency. The reason is rebase churn: the `main` ruleset's
`strict` setting makes every merge leave the other open PRs behind, and
Dependabot rebases and re-runs CI on all of them (see
[Dependabot rebases on its own](#dependabot-rebases-on-its-own)). With N PRs
that is roughly N + (N-1) + ... + 1 full CI runs.

- **Sensitive dependencies stay out.** The group's `exclude-patterns` equals
  `sensitive_dependencies` in `.github/automerge-config.json`. Auto-merge
  refuses a whole PR if any dependency in it matches one, so without the
  exclusion one sensitive bump would hold the entire batch for manual review.
  `tests/test_dependabot_config.py` fails when the two lists drift apart. The
  uv `dev-dependencies` group carries the same `exclude-patterns`, because its
  `types-*` pattern would otherwise catch e.g. `types-pyOpenSSL`.
- **Major bumps keep their own PRs** from the catch-all, because of
  `update-types`. Majors of `dev-dependencies` members (now including type
  stubs and build requirements) go into that group's PR instead, and
  auto-merge refuses a PR containing a major.
- **Order matters.** Per GitHub's `dependabot.yml` documentation, a dependency
  matching more than one group goes into the first one listed, so the catch-all
  is last, after `dev-dependencies` (uv) and `codeql-action` (github-actions).
  A test asserts this.
- **Trade-off:** one failing bump holds every update in its group until it is
  fixed or pinned (for example with an `ignore` entry in `dependabot.yml`).

### Updates the catch-all cannot take

dependabot-core's `SemverGroupingRules#allow_grouping?`
(`updater/lib/dependabot/updater/semver_grouping_rules.rb`) runs only for a
group with `update-types`, and returns `false` in two cases the catch-all hits
(#1231):

- **Only the fourth version component changed.** Type stubs version as
  `<upstream>.<date>` (`types-pyyaml` `6.0.12.20260906` to `6.0.12.20261030`),
  so major, minor and patch are all equal and the bump is never grouped.
- **No locked version.** `[build-system] requires` entries such as `hatchling`
  and `hatch-vcs` are not in `uv.lock`, so there is no current version to
  classify against.

A group without `update-types` skips that check. So the uv `dev-dependencies`
group, which has none, also lists `types-*`, `hatchling` and `hatch-vcs`,
rather than adding new groups that would each open another weekly PR.
`tests/test_dependabot_config.py` asserts that `types-pyyaml` and every
`[build-system] requires` entry land in it.

Known residual: any other dependency whose bump changes only the fourth
version component still arrives as its own PR. That is expected, not a
regression.

## Stale PRs

The `main` ruleset requires branches to be up to date before merging
(`required_status_checks` with `strict: true`). When `main` advances after
a dependabot PR is opened, the PR falls behind and cannot merge until it is
rebased.

### Dependabot rebases on its own

Normally nobody has to act. Dependabot rebases its open PRs and
force-pushes as `main` moves. The `synchronize` event re-runs the Merge
Gate and CI, and the auto-merge the workflow already enabled fires when
checks go green. A weekly batch of dependabot PRs clears this way without
anyone stepping in.

This is observed behaviour, not configured: no workflow in this repository
rebases dependabot PRs, and `.github/dependabot.yml` sets no
`rebase-strategy`, so Dependabot's default (`auto`) applies. On 2026-11-02,
PR #1160 got no rebase comment, yet the timeline
(`gh api repos/{owner}/{repo}/issues/1160/timeline`) shows
`dependabot[bot]` force-pushing it a few minutes after each other
dependabot PR merged:

| `main` merge | #1160 force-push (UTC) |
|---|---|
| 15:49 (#1164) | 15:51 |
| 15:55 (#1162) | 15:58 |
| 16:01 (#1163) | 16:04 |
| 16:07 (#1161) | 16:12 |
| 16:22 (#1159) | 16:24, then auto-merged at 16:28 |

What triggers the rebase is unconfirmed. Those bumps all touch `uv.lock`,
so each merge may have caused a real conflict, and `auto` rebases on
conflict. Dependabot may also rebase a PR that is only behind while
auto-merge is enabled. The timeline does not tell the two apart, so do not
rely on a PR that is behind with no conflict being rebased.

The cost is CI time: when each merge leaves the remaining PRs behind and
each is rebased, every one of them runs CI again, so a batch of N PRs can
cost up to N + (N-1) + … + 1 runs.

### Fallback: request the rebase

If a PR sits behind `main` and no `dependabot[bot]` force-push arrives,
ask for one:

```bash
gh pr comment <number> --body "@dependabot rebase"
```

Dependabot rebases the branch and force-pushes, and CI and auto-merge
proceed as above.

> [!IMPORTANT]
> The comment **must be posted by a real user** (your `gh` CLI auth, or
> the PR sidebar UI). Dependabot's command parser rejects `@dependabot`
> commands from GitHub Apps, including the App configured for this repo
> — see upstream issue
> [dependabot/dependabot-core#9147](https://github.com/dependabot/dependabot-core/issues/9147).
> Posting the rebase request from a workflow that authenticates as the
> App, or as `github-actions[bot]` via `GITHUB_TOKEN`, fails with
> *"Sorry, only users with push access can use that command."*

This also follows the signed-commit rule documented in the
[Dependabot PRs](../../AGENTS.md#dependabot-prs) section of `AGENTS.md`:
**never** call the GitHub `update-branch` API or rebase locally, because
both strip dependabot's verified commit signatures.

### Confirming the rebase landed

The force-push takes one to three minutes. **Do not request a second
`@dependabot rebase` until the first one lands** — the second request is
processed against the pre-rebase branch and the two can race.

Poll until the PR's first commit has current `main` as its parent:

```bash
main_sha=$(gh api repos/{owner}/{repo}/git/ref/heads/main --jq '.object.sha[0:7]')
gh api repos/{owner}/{repo}/pulls/<number>/commits --jq '.[0].parents[0].sha[0:7]'
```

When those match, wait for CI (`gh pr checks <number> --watch`) and merge
with `doit pr_merge --pr=<number>`.
